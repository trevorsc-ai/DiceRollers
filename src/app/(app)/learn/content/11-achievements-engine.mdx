The achievements engine is the most performance-sensitive code in DiceRollers. It runs on **every single roll** — every time anyone saves dice, this code decides what badges they just earned. If it gets slow or noisy, every roll feels slow.

CLAUDE.md is blunt: this is the **hot path**. Treat it that way.

## The rule that shapes everything

> **One bulk fetch up front, then derive everything from it in memory. Do not add new individual count queries.**

There are 40+ achievements in this app. The naive approach would be: for each achievement, run a separate Postgres query (`SELECT COUNT(*) WHERE ...`). With 40 achievements, that's 40 round trips on every roll. The user would feel it.

The engine does the opposite: **one big query** pulls in everything the engine could possibly need (the user's rolls, their existing achievements, twinsies data, punch card progress). Then every check is a pure JS calculation over that in-memory data. 1 query, 40 checks.

## Why string IDs are forbidden

You'll see this in CLAUDE.md too: **never hardcode achievement IDs as strings**. Use the constants from `src/lib/achievementIds.ts`.

## Adding a new achievement (the recipe)

Per CLAUDE.md:

1. Add the ID constant to `src/lib/achievementIds.ts` first.
2. Add a matching row in the DB seed migration so the achievement exists in `achievements`.
3. Inside `processAchievements`, add your check using `queueCompletion` or `queueCounter`. **Derive** your condition from the bulk-fetched data — don't run a new query.
4. If it's a repeatable achievement with a side table (punch card, twinsies), it gets its own dedicated write — that's the documented exception.

## What you can do with this knowledge

When planning a new achievement, ask first: *can this be derived from data the engine already loads?* If yes, add a check next to the others. If no — if the rule genuinely needs new data — extend the bulk fetch (carefully), don't sneak in a per-achievement query. That preserves the performance the engine was designed around.
