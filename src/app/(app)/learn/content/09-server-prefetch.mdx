If TanStack Query is the client-side cache, and the server can already talk to the database directly... how do those two worlds meet? The answer is **hydration**: the server pre-fills the cache, ships it embedded in the HTML, and the client picks up where the server left off.

That's why pages in this app load fast and don't flicker.

## The template

  code={`import { HydrationBoundary, dehydrate } from "@tanstack/react-query";
import { createClient } from "@/lib/supabase/server";
import { createQueryClient } from "@/lib/queryClient";
import { rollsQueryKey, fetchRolls } from "@/lib/queries/rolls";
import FeedView from "./FeedView";

export default async function FeedPage() {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  if (!user) redirect("/login");

  const queryClient = createQueryClient();
  await queryClient.prefetchQuery({
    queryKey: rollsQueryKey(),
    queryFn: () => fetchRolls(supabase),
  });

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      <FeedView userId={user.id} />
    </HydrationBoundary>
  );
}`}

## Why this matters

Without hydration, your page would render once on the server (with the data), then re-render on the client (without the data, with a spinner), then re-render again when the client finally finishes its own fetch. Users see a flash, an empty state, then content. That's the classic "Single Page App" UX papercut.

With hydration, the server-rendered HTML already includes the rendered list. The client picks up the same cache, sees data is fresh, and skips fetching entirely.

## A subtle gotcha

The fetch function has to be **isomorphic** — same code works on server and client. That's why `fetchRolls(supabase)` takes the client as an argument. If you accidentally use `createClient` from `@/lib/supabase/server` inside a fetch function called from the client, you'll get a build error (or worse, a runtime error in the browser).

This is why CLAUDE.md insists: query keys and fetch functions live in `src/lib/queries/`, and the fetch fn ALWAYS accepts a `SupabaseClient`. That single convention is what makes server + client hydration safe.

## What you can do with this knowledge

When a page feels slow on first load, ask: *is the server prefetching the data this page needs?* If not, add a `prefetchQuery` block. The cost is one extra await on the server (it would've happened anyway on the client); the win is no client-side spinner.
