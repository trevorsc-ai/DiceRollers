A web app is just three things talking to each other: a **browser**, a **server**, and a **database**. Everything else — frameworks, deployment pipelines, all of it — is plumbing around that core triangle.

## The three players

**The browser** runs on your phone or computer. It downloads HTML, CSS, and JavaScript, then renders the page you see. When you tap a button, the browser decides whether to handle it locally (toggle a menu) or send it to the server (save a roll).

**The server** runs somewhere in the cloud — for DiceRollers, on Vercel. It receives requests, talks to the database, sometimes does heavy computation (like figuring out which achievements you just earned), and sends a response back.

**The database** is where the real data lives — your rolls, your friends, the achievement records. For us, that's Postgres, managed by Supabase. The server is the only thing that ever speaks directly to the database.

## Where each of these lives in this repo

Open the file tree. Every box in the diagram above corresponds to a folder:

- **Browser code** lives in everything ending with `View.tsx` or marked `"use client"` at the top. This is the React UI your phone runs.
- **Server code** lives in `page.tsx` files (without `"use client"`), and in `src/app/api/*/route.ts` (the API endpoints).
- **Database access** is wrapped by `src/lib/supabase/` (one client for the browser side, another for the server) and the SQL migrations in `supabase/migrations/`.

That split — where each piece of code runs — is the first big mental model. Next module: how URLs find their way into the right folder.

## What you can do with this knowledge

When something feels slow, ask: *which leg of the trip is the problem?* Is the browser doing too much (re-rendering, big bundle)? Is the server doing too much (slow query, expensive computation)? Is the database the bottleneck (missing index)? "It's slow" is unsolvable; "the database query is slow" has obvious next steps.
