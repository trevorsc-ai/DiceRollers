## What the client does on success

The Roll page wraps the API call in `useMutation`. Here's the celebration logic in plain English:

1. **Invalidate caches** — `useQuery({ queryKey: rollsQueryKey() })` consumers refetch in the background.
2. **Store newly-earned achievement IDs in localStorage** — read by BottomNav's `checkDot()` to light up the pink notification dot on the Achievements tab.
3. **Fire visual celebrations** — DoublesConfetti for doubles, MalortCelebration for a Malört roll, DailyDoubleCelebration if today's rotating logo aligns.
4. **Reset the dice picker for the next roll.**

That's why a single tap produces a chain of effects — the architecture is deliberately set up so each effect is a small, independent piece of code, all triggered by the same API success.

## Failure modes worth knowing

- **Network drops mid-save.** The optimistic celebration would be wrong, so we *don't* go optimistic on saves — we wait. The user briefly sees a disabled button until the network responds. Acceptable trade-off for correctness.
- **Achievements engine throws.** We treat this as fatal for the request — better to fail the save than to silently miss awarding badges. The error surfaces in the response.
- **Two saves in flight at once.** The button is disabled while `mutation.isPending` is true. No double-submit possible.

## What you can do with this knowledge

When planning a new "user takes an action that affects multiple things" feature, mirror this shape: one API route handles the write, one engine derives all the consequences synchronously, one response packages everything the client needs. Distributed side-effects (multiple endpoints, queues, etc.) are tempting but usually overkill for an app at this scale.
