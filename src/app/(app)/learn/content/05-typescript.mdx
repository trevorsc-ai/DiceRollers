TypeScript is JavaScript with **types**. You annotate what shape your data has, and the compiler catches a huge category of bugs *before* you ever run the code. In this codebase, strict mode is on, so the compiler is opinionated. That's a feature.

## The three you'll see everywhere

```ts
// 1. Primitive types
const username: string = "travis";
const count: number = 42;
const isAdmin: boolean = true;

// 2. Arrays
const drinks: string[] = ["beer", "shot", "wine"];

// 3. Objects (via interface or type)
interface Roll {
  id: string;
  user_id: string;
  drink: string;
  is_doubles: boolean;
  created_at: string;
}
```

Anywhere a function takes an argument or returns a value, TypeScript wants to know its shape.

## The Database type — TypeScript's masterpiece in this app

## Interfaces vs. types — they're almost the same

You'll see both:

```ts
interface User { id: string; name: string }
type User = { id: string; name: string }
```

In practice, they're interchangeable. Use `interface` for object shapes (it's what most of the codebase does), `type` when you need a union (`type Status = "idle" | "loading" | "error"`) or a computed type.

## What you can do with this knowledge

When you spot a TypeScript error, *read it* — TS error messages are wordy but precise. They almost always tell you the exact mismatch ("expected `string | Date`, got `number`"). Resist the urge to slap `any` on something to make the error go away; nine times out of ten the compiler is catching a real bug.
